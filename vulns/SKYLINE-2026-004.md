## Description

CUCM 15 validates OAuth Bearer access tokens by **pure local cryptography**: RS256 JWS verification plus direct JWE decryption of an inner claims object (`sub`, `ccid`, `ctyp`, `exp`, `siss`, `scopes`, …), using RSA and symmetric keys loaded at startup from the `authzkeys` database table (event-driven reload only — no key TTL, no revocation list, no per-token issuance record). The `sub` claim becomes the authenticated `user_id` verbatim. `BearerAuthenticationRequestHandler` hardcodes the request as proxy-forwarded and creates the principal directly for any token whose `client_id` is not one of five hard-coded Jabber client IDs — device-class tokens mint **zero-database principals**. The failure throttle counts only *failed* attempts; the password-lockout machinery is entirely off-path. A valid forged token therefore authenticates with **no DB footprint, no lockout, no throttle, and no audit counter**.

The signing keys are the whole trust anchor, and they are extractable by any process with CUCM root — obtainable pre-authentication via the published Silent;Call (SKYLINE-2026-001→003) or Dead;Dial (057a/b) chains, both CVSS 10.0. An offline forge harness was validated **6/6 against the product's own validator as oracle**: full-spec forgery returns the chosen `user_id` (including `sub=administrator`); expired, signature-tampered, and bad-`siss` tokens are correctly rejected — the validator genuinely validates, which is what makes the positive result meaningful.

Confirmed live on 2026-09-27: a freshly minted forged token (`sub=administrator`) presented through the Expressway MRA corridor from the internet side caused CUCM's SSO filter to issue a `JSESSIONIDSSO` session cookie (404 path-miss + session issuance, byte-stable signature).

Resolved live on 2026-09-28: the single 401 observed in the first proof was not an authorization decision — the UDS user-resource gate (`UDSFilter`) enforces a *self-only name-equality rule* (authenticated name must equal the URL-path user), with zero role checks behind it. With a `sub`-matched forged token (`sub=<path-user>`), the corridor delivered the full user record (200), its credentials view (200), and a credential write (PIN reset, **204 — no old PIN required, no ownership check**), verified after the fact in the product's Informix database. Internet-origin, zero real credentials in the path, silent on every abuse-defense telemetry source. Practical severity: per-user account and voicemail-PIN takeover for every user the cluster keys can name.

## Affected Configuration

- `authzkeys` table (RSA private + JWE symmetric keys, CCMEncryption-encrypted at rest) readable by any root-context process; keys never expire absent explicit rotation.
- `validateAccessToken`: local crypto only — no DB, no revocation check, no audience/path binding (a token minted for SSO flows validates on any Bearer-accepting webapp).
- `BearerAuthenticationRequestHandler` L147–160: `isHaproxyRequest=true` hardcoded; `CCMRealmPlugin.createPrincipal` invoked from token claims without DB identity binding for non-Jabber `client_id`s.

## Fix

1. Bind token acceptance to issuance state: per-token (or per-`jti`) revocation/issuance records checked at validation, or short key-TTL with enforced rotation.
2. Restrict Bearer acceptance by audience/path — tokens minted for SSO flows must not validate on arbitrary webapps.
3. Alert on `JSESSIONIDSSO` issuance without a corresponding IdP authentication event (detectable today; see False;Relay mitigations.md).
4. Treat `authzkeys` compromise as a cluster-wide credential breach: document and tool key rotation as an incident-response step.
