## Description

On the internet-facing Expressway-E, the MRA relay lane applies `ts_auth` in **`check-exist`** mode: the gate tests only that the `X-Auth` session cookie is present and non-empty. All cryptographic validation (`sha512(edgeSalt ‖ cookie)` against the token store) is deferred to the inner Expressway-C. The DMZ edge — the component whose purpose is to gate the internet — makes no independent credential decision on relay traffic.

Consequences, live-confirmed:

1. An unauthenticated internet attacker reaches C's validation surface and the descriptor-prefix routing logic with a cookie of arbitrary content; E logs relayed rejections as normal traffic.
2. Trust is inverted: the untrusted-side box trusts, the trusted-side box verifies — over a tunnel that lands on C's **loopback** interface, where C's zero-auth configuration API also listens (SKYLINE-2026-006). Any weakness in C's validation data is automatically internet-reachable, with no compensating edge check.
3. Combined with any cookie C will accept (a legitimate MRA login, or a seeded record), E forwards the request to the client-selected internal descriptor without further identity scrutiny.

Confirmed live on 2026-09-27 from the internet side: empty/garbage-cookie requests were relayed to C (C-issued 407/401 signatures returned through E); presence of a C-valid cookie opened the corridor to internal CUCM (200 UDS data, SSO-session issuance) with E contributing no validation beyond existence.

## Affected Configuration

Live remap chain on E (read from the running box):

```
catch-all / → ts_sso_flow_remap (--fqdn <edge fqdn>, whitelist) → ts_x_route_remap
            → ts_auth check-exist (edge_auth.conf)          ← presence-only
            → ts_whitelist_remap
```

Contrast: C-side `ts_auth` runs in verify mode against the CDB token store.

## Fix

1. Perform cryptographic validation (or at minimum a signed/MAC'd existence check) at E — the internet-facing box must not forward unvalidated session material into the trusted network.
2. Bind cookies to presentation context (client IP hash / TLS session) so a relayed cookie cannot be replayed from a different source.
3. Log and rate-limit relayed rejections distinctly from E-local ones, so brute-force against C's validator is visible at the edge.
