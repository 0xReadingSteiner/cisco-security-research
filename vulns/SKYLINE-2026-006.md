## Description

Expressway-C's CDB configuration API listens on loopback port 4370 and authenticates **no one**. The MRA relay's `X-Auth` session tokens validate as CDB rows binding `{username, H = sha512(edgeSalt_bytes ‖ cookie_value), expiry}`. Any process on C — any user, including unprivileged service accounts — can therefore insert a token record for an attacker-chosen cookie value, and from that moment:

- C's `ts_auth` cryptographic verify passes the planted cookie (hash match, AUTHORISER lookup exact);
- E's presence-only gate (SKYLINE-2026-005) already passes it;
- the descriptor corridor to internal CUCM is open **from the internet with no MRA credentials existing anywhere in the chain**.

Confirmed live on 2026-09-27 (Phase A of the corridor fire): one planted record (census: exactly 1 record, hash-verified) carried internet-side requests to CUCM — S1 reachability signature, forged-Bearer acceptance (`JSESSIONIDSSO` issued), and HTTP 200 with live UDS XML out of the LAN. Record deleted after the test; census returned to 0.

Severity context: this release of Expressway-C ships **two independent local root chains** — zero-auth CDB → `csvfilter` command injection → unprivileged RCE → root, and a world-readable Erlang distribution cookie + `verify_none` distribution listener → root (both reported to the vendor separately, both HIGH). The appliance's security model assumes no untrusted local code ever runs; Seedhack is what that assumption costs when it fails — and it makes every foothold on C, at any privilege level, into an internet-facing credential mint.

## Affected Configuration

- CDB API on 127.0.0.1:4370: no authentication, no peer credentials check, full write access to configuration tables including the token store.
- Token validation reads only the CDB row set — no cross-check against ECS issuance logs, no per-record provenance.

## Fix

1. Authenticate the loopback CDB API (peer-credentials / mTLS / per-service keys) — zero-auth local APIs are network-reachable the moment any SSRF, tunnel misroute, or foothold exists.
2. Sign or provenance-stamp token records at issuance (ECS-only write path) so planted rows fail validation.
3. Alert on token-store rows that do not correspond to an ECS `Authenticated user successfully` issuance event (detection rule in False;Relay mitigations.md §2.2).
