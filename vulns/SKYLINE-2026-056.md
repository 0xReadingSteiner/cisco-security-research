## Description

The Expressway SIP stack converts the `Content-Length` header value with `ttclib_strToUInt()`, a 32-bit accumulator loop with no overflow check. `Content-Length: 4294967296` (2³²) wraps to 0: the parser believes the message has an empty body and treats the remaining bytes on the TCP connection as a new, independent SIP request.

An unauthenticated attacker can therefore smuggle a second SIP dialog through the edge proxy inside what the parser — and any inspecting firewall or IDS — believes is body data. The smuggled request bypasses zone-policy evaluation and per-request logging, and reaches internal B2B peers (CUCM, CUPS, IM&P) appearing to originate from Expressway's trusted internal address.

Confirmed live against Cisco Expressway X14.3.7 on 2026-08-09/10: a single TCP connection produced six SIP responses, including `100 Trying` and `480 Temporarily Not Available` for the smuggled INVITE's own Call-ID — proof the smuggled request was processed as a fully independent dialog.

## Affected Code

Reconstructed logic (binary analysis, debug symbols present):

```c
unsigned int ttclib_strToUInt(const char *str) {
    unsigned int result = 0;              /* 32-bit */
    while (*str >= '0' && *str <= '9') {
        result = result * 10 + (*str - '0');  /* NO OVERFLOW CHECK */
        str++;
    }
    return result;
}
```

No maximum Content-Length validation and no body-length-vs-framing verification exist at the caller. The same parsing code likely exists across Expressway X14.x and possibly earlier.

## Fix

1. Parse `Content-Length` in 64-bit arithmetic (or check `result > (UINT32_MAX - digit) / 10` each iteration) and reject on overflow.
2. Reject messages whose `Content-Length` exceeds a sane SIP maximum (e.g. 64 KiB) outright.
3. Enforce message framing: after reading the declared body length, do not begin parsing a new request until the transport layer confirms the previous message was fully consumed and the connection's dialog state permits pipelining.
